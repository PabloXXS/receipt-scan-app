# Дизайн: серверное распознавание позиций чека (магазин-агностичный)

Дата: 2026-06-15
Статус: согласование дизайна (brainstorming → план)

## Проблема

Распознавание позиций сейчас целиком на клиенте (iOS): Apple Vision (`scan/ocr`
MethodChannel) → эвристический парсер `ReceiptParserImpl`. Подход:

- привязан к **одному формату** (ProStore/РБ): заголовок позиции = `<штрихкод 6+ цифр>
  <название>`, разделитель `*`, граница зоны — слово `ИТОГО`;
- теряет **геометрию** в нативном слое — из каждого наблюдения берётся только
  `boundingBox.maxY`, X-координата выбрасывается, колонки «цена/кол-во/сумма»
  схлопываются в плоский поток строк;
- **только iOS** (нет кроссплатформенности);
- нет **confidence** и **сверки** с печатным итогом.

**Цель:** распознавать позиции **любого** чека независимо от магазина и страны,
бесплатно, кроссплатформенно. Разбор переносится на сервер (PHP-воркер + OCR-сервис),
клиент только снимает фото и показывает результат.

## Решения (зафиксированы при brainstorming)

| Вопрос | Решение |
|---|---|
| Главный драйвер | Поддержка многих магазинов/стран (обобщение) |
| Ограничения | Бесплатно; разбор на PHP-воркере; фото обрабатывается на сервере |
| Движок OCR | **PaddleOCR** (вариант C) — единственный бесплатный движок с кириллицей, боксами и confidence на обе платформы |
| Поток данных | **Асинхронно: pgmq + Realtime** (возврат к изначально заложенному в data-flow.md) |
| iOS-Vision | **Убираем полностью** — сервер единственный путь |
| Привязка к магазинам | **Нет.** Один магазин-агностичный алгоритм (геометрия + арифметика + классы лексем). Профили сетей в v1 не вводятся |
| Подтверждение после ревью | **RPC `confirm_receipt` (`SECURITY DEFINER`)**; промежуточный статус `review` |
| Язык/место парсера | **Python, внутри OCR-сервиса** — сервис возвращает сразу позиции; PHP-воркер тонкий (фото → сервис → persist) |

### Почему PaddleOCR

Нет бесплатного движка, который одновременно (а) on-device кроссплатформенно и
(б) хорошо распознаёт кириллицу:

- Apple Vision — отлично, но только iOS.
- Google ML Kit (Android) — **не поддерживает кириллицу** (только Latin/Chinese/
  Devanagari/Japanese/Korean).
- Tesseract (сервер, PHP-native) — слабо на фото термочека без тяжёлого препроцессинга.
- **PaddleOCR (сервер)** — выделенная cyrillic-модель (ru/be/uk), боксы + **confidence**,
  обучен на «диких» фото; цена — Python-сайдкар рядом с PHP.

Источники: ML Kit supported languages
(https://developers.google.com/ml-kit/vision/text-recognition/v2/languages);
PaddleOCR cyrillic_PP-OCRv5_mobile_rec
(https://huggingface.co/PaddlePaddle/cyrillic_PP-OCRv5_mobile_rec).

Приватность: фото **уже сегодня** уезжает в Storage (best-effort), воркер
(service-role) и так имеет к нему доступ → серверный OCR не добавляет нового слива.

## Архитектура и поток данных

```
[Клиент Flutter]                    [Supabase]                 [Воркер + OCR-сервис]
 камера/галерея
   │ сжатие JPEG ≤1600/q80
   │ QR-детект на устройстве (УИ)
   ├─► upload фото ───────────────► Storage (bucket receipts)
   ├─► INSERT receipts
   │   status=processing, source=ocr,
   │   photo_path, qr_raw           ──► trigger receipts_enqueue
   │                                      └─► pgmq receipts_processing
   │                                                │
   │                                                ▼
   │                                        ReceiptProcessor:
   │                                         1 FetchFiscalData (NullProvider)
   │                                         2 OCR+Parse: скачать фото (service-role)
   │                                           └─HTTP─► OCR-сервис (PaddleOCR+парсер)
   │                                                    возвращает ПОЗИЦИИ
   │                                                    {items[], total?, confidence}
   │                                         3 (парсинг — внутри сервиса)
   │                                         4 Normalize (позже)
   │                                         5 Persist: receipt_items, total,
   │                                           status=review (или failed+error)
   │                                                │
   ◄── Realtime (подписка receipts + receipt_items) ┘
   ▼
 Экран-ревью: позиции + подсветка низкого confidence
   │ правка/удаление
   ▼
 RPC confirm_receipt → status=done, пересчёт total
```

Принципы: один движок на обе платформы; разбор обновляется без релиза приложения;
очередь pgmq даёт ретраи/надёжность; PHP — оркестратор, Python — только инференс.

## Компонент 1 — Магазин-агностичный парсер (ядро)

Чистая функция `List<Observation> → ReceiptData`, где
`Observation = {text, bbox{x,y,w,h}, confidence}`. Без сети и БД. Опирается на
универсальные инварианты, а не на признаки конкретной сети.

1. **Сборка строк.** Кластеризация наблюдений по `y` (перекрытие) → визуальные
   строки; внутри строки сортировка по `x`.
2. **Денежная колонка.** Самый правый вертикальный кластер токенов `\d+[.,]\d{2}`
   (десятичная `,`/`.` нормализуются). Якорь, не зависящий от языка/валюты.
3. **Инференс ролей колонок арифметикой.** В зоне позиций 1–3 числовых колонок
   (цена/кол-во/сумма) в разном порядке. Роли выбираем перебором так, чтобы
   `a × b ≈ c` выполнялось на большинстве строк. Весовые позиции
   (`15.77 × 0.562 = 8.86`) — тем же правилом. **Роли выводятся из математики, а не
   из заголовков колонок или символа-разделителя.**
4. **Классы лексем вместо ключевых слов сети.** Денежный токен / целое / алфавитная
   строка / длинный цифровой код (опциональный штрихкод). Позиция = строка с
   алфавитным названием слева и суммой справа. Штрихкод-префикс **не требуется**.
5. **Многострочные названия.** Строки без денежного токена, выровненные под колонкой
   названия, прицепляются к ближайшей позиции. Числовой мусор в название не тянем.
6. **Границы зоны — самоопределяемые.** Зона позиций = максимальная непрерывная
   полоса строк с суммой в доминирующей денежной колонке + названием. Итог берём не
   по слову, а как «наибольшее денежное значение под зоной, ≈ сумме позиций» —
   самопроверяющийся языконезависимый якорь.
7. **Сверка и confidence.** `sum(items)` против найденного итога: сошлось → высокая
   уверенность; разошлось → понижение + пометка. Confidence позиции =
   f(OCR-confidence строк, выполнение `unit×qty≈sum`, полнота полей). Питает подсветку
   сомнительных позиций в ревью.

### Границы универсальности (честно)

Детерминированный парсер не даёт 100%. Хвост (~5–10%): чеки без печатного итога,
скидочные/бонусные строки (`-2.00`), очень шумный OCR. Стратегия для хвоста —
**не правила под магазин**, а:

- общие эвристики (отрицательные суммы → строки-скидки, прицепляются к предыдущей
  позиции, а не отдельная позиция);
- **confidence + сверка → подсветка в ревью**: где парсер не уверен, не угадываем, а
  просим пользователя проверить (экран ревью и так есть).

### Изоляция

Геометрия / денежная логика / склейка названий / границы зоны — отдельные тестируемые
куски. Профили сетей в v1 **не вводятся**; если когда-то понадобятся для патологичного
формата — чисто опциональный оверрайд, по умолчанию пустой (вне рамок этого плана).

**Язык/место — решено:** парсер живёт в **Python внутри OCR-сервиса** (Компонент 2).
Сервис возвращает сразу позиции, а не сырые строки. Преимущества: геометрия/
кластеризация удобнее (numpy), тесты pytest гоняются **локально** (для тестов парсера
PaddleOCR не нужен — он работает на фикстурах геометрии), PHP-воркер становится тонким.
Парсер реализуется как **чистый модуль** (`Observation[] → ParsedReceipt`), отделённый
от PaddleOCR-адаптера и FastAPI-слоя, чтобы тестироваться без тяжёлых зависимостей.

## Компонент 2 — OCR-сервис на Python (PaddleOCR + парсер)

Объединяет движок и разбор. Внутри — три изолированных слоя:

- **PaddleOCR-адаптер** — фото-байты → `Observation[] {text, bbox{x,y,w,h},
  confidence}`. **Реализация на PaddleOCR 2.x** (`lang="cyrillic"`, PP-OCRv4
  cyrillic-модель) — стабильный, хорошо документированный 2.x-контракт `[poly,
  (text,conf)]`; CPU-инференс; веса в образе. Апгрейд на 3.x / `cyrillic_PP-OCRv5_mobile_rec`
  (выше точность) — будущий шаг, требует миграции API (`.predict()`, иной формат).
  Препроцессинг: grayscale → нормализация контраста (дескью/бинаризация — TODO).
- **Парсер** (Компонент 1) — чистый модуль `Observation[] → ParsedReceipt`, без сети/
  тяжёлых зависимостей, тестируется на фикстурах.
- **FastAPI-слой** — `POST /ocr` (JPEG-байты) → `{ items: [{raw_name, qty, unit_price,
  sum, confidence, barcode?}], total?, confidence }`. Без БД, без состояния.

Деплой: отдельный Docker-образ рядом с воркером; `OCR_SERVICE_URL`, внутренняя сеть.
Сервис ничего не знает про Supabase. Контракт фиксируется в новом ADR и в `data-flow.md`.

## Компонент 3 — Воркер (тонкий, реализация заглушек)

- `ReceiptProcessor` — оркестрация: Fetch(Null) → OCR+Parse(сервис) → Normalize(позже)
  → Persist.
- OCR-шаг (на базе `OcrFallbackStep`, становится основным) — скачивает фото из Storage
  (service-role), вызывает OCR-сервис по HTTP, получает **готовые позиции**.
- `ReceiptOcrParser` (PHP) — становится **тонким клиентом HTTP** к OCR-сервису
  (десериализация ответа в `ReceiptData`), без логики разбора геометрии.
- `PersistReceiptStep` — пишет `receipt_items`, `total`, `status=review|failed`,
  `error`.
- Семантика pgmq как есть: успех → delete, ошибка → retry, исчерпание → archive +
  `status=failed`.

## Компонент 4 — Клиент (Flutter)

1. Захват → сжатие → QR-детект на устройстве (УИ) → upload фото → `INSERT
   receipts(status=processing, source=ocr, photo_path, qr_raw)`.
2. Экран «Обрабатываем чек…» + Realtime-подписка на строку `receipts` и
   `receipt_items` (`core/realtime/` сейчас пуст — реализуется здесь).
3. По событию (status `review`) → экран-ревью с позициями и подсветкой низкого
   confidence.
4. Правка/удаление → **RPC `confirm_receipt`** (атомарно: правки позиций +
   `status=done` + пересчёт `total`).

**Удаляется:** `VisionOcrEngine`, `ReceiptParserImpl` и Swift-OCR (`ReceiptOcr` в
`AppDelegate.swift`), нативный канал `scan/ocr`. (QR-детект на устройстве остаётся —
способ уточняется на этапе плана с учётом памяти про `mobile_scanner`/симулятор.)

## Изменения схемы БД

- Статус `review` в enum/check `receipts.status` (поток `processing → review → done |
  failed`).
- RPC `confirm_receipt(receipt_id, items_payload, total)` — `SECURITY DEFINER`:
  проверяет владение, фиксирует правки `receipt_items`, ставит `status=done`,
  пересчитывает `total`. Без расширения UPDATE-политики на всю таблицу `receipts`.
- `receipt_items` пишет воркер (service-role) — RLS зоны B уже позволяет.

Любое изменение схемы цен/публикации не затрагивается; путь фото→OCR не задевает
зону C. Миграцию и RPC проверяет субагент `privacy-rls-reviewer`.

## Тестирование

- **Парсер** — основной фокус: разнородные фикстуры `Observation[] → ReceiptData`
  (ProStore + другие сети/страны) на проверку универсальности; юнит-тесты на каждый
  кусок (сборка строк, инференс ролей `a×b≈c`, склейка названий, границы зоны, сверка).
  Дополняем существующий `prostore_ocr_fixture.dart` геометрией.
- **OCR-сервис** — тесты контракта вход/выход; парсер от сервиса не зависит (фикстуры
  геометрии).
- **Воркер** — phpunit на шаги (мок HTTP OCR-сервиса, мок Storage/Supabase). Реальный
  прогон — CI (PHP локально не установлен).
- **Приватность** — `privacy-rls-reviewer` на миграцию `review`/RPC и путь фото→сервис.

## Вне рамок (YAGNI)

- Профили конкретных сетей/магазинов.
- LLM/облачный OCR и платные тиры.
- Фискальные API (в РБ легального «позиции по QR» нет).
- Нормализация в канонический каталог (`ProductNormalizer`) — отдельный цикл.
- Очистка осиротевших фото в Storage — отдельная задача.
